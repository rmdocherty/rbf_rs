So what's a bilateral filter?

Computer programs tend to store images as 2D arrays of numbers. For a simple greyscale image, this is a 2D array where the value for the pixel (x,y) is an integer between 0 and 255 that says how bright that pixel should be. For a colour image this is 3 numbers representing the (R)ed, (G)reen and (B)lue channels respectively. A black pixel is [0, 0, 0], a red pixel [255, 0, 0] and a white pixel is [255, 255, 255].

An 'image filter' takes your input image (represented as a [H, W, 3] array of numbers) and performs some mathematical operation on it. This can be blurring, sharpening, looking for edges, and so on. People like to use a blur filter (usually some form of Gausisan blur) to reduce noise in an image - typically these blurs work by averaging values in a local neighbourhood around each pixel.

The classic Gaussian blur works as follows: for each pixel in the image, look at all the other pixels within a radius R (this is the local neighbourhood, often called a kernel), and do a weighted average of all the pixel values. This weighting is based on Gaussian distribution (hence the name) with a standard deviation of σ_spatial, such that nearby pixels have a strong weight and far away pixels have a low weight.

The problem with the Gaussian blur is that it's not 'edge aware' - it can and does spread information across sharp boundaries in image colour. One solution to this is the 'bilateral filter', which does the weighted average of pixels in the neighbourhood, but with two weights: a spatial weight (as for the Gaussian blur) and weight based on the colour distance of the two pixels (σ_range). For three pixels, P0 = [128, 128, 128], P1 = [140, 140, 128] and P2 = [128, 128, 90], the (Euclidean) colour distances are dist(P0,P1) = √{(140 - 128)^2 + (140 - 128)^2} = 16.7, dist(P0,P2) = √{(128 - 90)^2} = 38.

The fact that colour distances are included in the weights means that pixels that are very different in colour won't be averaged, even if they're right next to each other physically - this is how the bilateral filter preserves edges. There is an associated computational cost: bilateral filters are much slower than a Gaussian blur (for various reasons they are more difficult to optimise).

And what's so recursive about it?

The slowness of traditional bilateral filters motivated some fancy ways of speeding it up. Qingxiong Yang proposed the 'Recursive Bilateral Filter' in 2012 which approximates the colour distance from pixel p to pixel q by accumulating the colour distances of all the pixels between p and q inside some internal state. This is why it's recursive: RBF(p_i) = a F(p_i) + RBF(p_i-1). This is neat because it means the runtime is only a function of the number of pixels (and channels) in the image, and not the size of local neighbourhood/kernel.

It also means the filter is separable - it can be run as a 1D horizontal pass followed by a 1D vertical pass (rather than over a 2D local neighbourhood at every pixel). Technically it's two horizontal passes and two vertical passes - one to incorporate forward/causal information (left-to-right accumulation), and one to incorporare reverse/anti-causal information. Not only does the separability reduce the total number of operations we need to do, it also makes the algorithm much more amenable to parallelism, i.e. splitting up work into separate chunks so our CPU(s) can process them more efficiently (think chopping your veg whilst the meat cooks).

All the boring implementation details

I've effectively ported this dude's C++ Recursive Bilateral Filter to Rust (this other guy has an RBF in Rust, but it's full of `unsafe` calls and is pretty unreadable), using the 'Rayon' crate for super easy parallelism. This gives us some pretty nice speed-ups: 3.14ms for my threaded Rust RBF vs 20ms for the single-threaded C++ RBF. I was pretty lazy in the end and just implemented a parallelized horizontal pass, then transposed the image and filtered rather than writing an explict vertical pass - there's probably a speed-up to be had there.

I then wanted to get a web-demo working, which turned out to be a real headache. Compiling rust to wasm is pretty straightforward, but compiling multi-threaded rayon code to wasm is not. There were a bunch of compiler flags & CORs headers I had to set, and I had to use the 'wasm-bindgen-rayon' crate too. I suppose this branch can stand as an example for getting rayon wasm working in 2026 (as well as a testament to man's folly).
